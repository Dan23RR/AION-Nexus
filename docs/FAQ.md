# Frequently Asked Questions — AION-NEXUS

Anticipated questions from technical reviewers, prospective customers, and integrators. Updated as new questions arrive.

## Verification & accuracy

### Q1. How do I know the F1 numbers (0.898 / 0.615 / 0.672) are real?

Three layers of evidence:

1. **Cross-source agreement**: the same numbers appear in 4 independent JSON result files (`final_results.json`, `cross_validation_results.json`, `mfpt_sensitivity_results.json`, `aion_nexus_training.log`) generated by the original training run on 2025-10-01.
2. **Analytical architecture verification**: the parameter count of 1,061,724 was independently re-derived from the architecture spec (multi-scale CNN + attention + BiGRU + classifier) — `delta = 0` against the training log. See `tests/test_smoke.py::test_model_param_count`.
3. **Independent runtime verification**: run `python -m scripts.verify_checkpoint --checkpoint checkpoints/aion_nexus_v1.pth --femto-test data/femto_test --mfpt data/mfpt`. The script asserts F1 within ±0.005 of published numbers and FAILs the build if numbers diverge.

### Q2. Why is the parameter count 1,061,724 when the design doc said ~505K?

The design doc was wrong. The 505K estimate did not account for the BiGRU (which alone is 543,744 params). The actual architecture, log-confirmed and re-derived analytically, is 1,061,724 params. We chose to keep the production architecture identical to what was trained — changing it would invalidate the published F1 numbers.

### Q3. Are the splits temporal or stratified?

The training log records `GLOBALLY STRATIFIED splits (Solution D)`. The original design called for purely temporal splits with a 5% gap; the released training run used global stratification. This is **documented as a divergence from design spec** in `MODEL_CARD.md` Training Data section. Future versions may revisit.

### Q4. What if my dataset shows different F1?

Expected. The model was trained on FEMTO. On a different dataset:

- 0.5–0.7 F1 zero-shot is normal cross-domain.
- Use `examples/03_few_shot_adaptation.py` with 10 samples/class to lift +5 to +10 percentage points.
- If still unacceptable, the gap is too large for transfer — retrain from scratch on combined data.

### Q5. How do you compute Cohen's d?

Pooled standard deviation: `d = (mean(A) - mean(B)) / sqrt((var(A) + var(B)) / 2)`. For lower-is-better metrics (NRMSE), negate the sign. Note: this package does not ship a `cohens_d` helper (an earlier revision of this FAQ pointed to `aion_nexus.utils.cohens_d`, which does not exist) — compute it with the one-line formula above or `scipy`/`numpy` directly.

## Architecture

### Q6. Why multi-scale CNN with kernels 3, 7, 15, 31, 63, 127?

Bearing fault frequencies span ~3 orders of magnitude. Outer-race faults manifest at high frequency (BPFO ~ 100 Hz scaled by RPM); cage faults at low (FTF ~ 1 Hz). Single-kernel CNNs miss one band. Three parallel branches at small / medium / large kernels capture all bands. The specific kernel sizes were picked to roughly cover these bands at 25.6 kHz sampling rate. Ablation in `PERFORMANCE_BENCHMARKS.md` shows multi-scale removal costs **−20 pp F1 cross-domain**.

### Q7. Why bidirectional GRU and not unidirectional?

Bearing degradation is a temporal process; both forward (causal) and backward (anticipatory pattern) context help disambiguate the current state. Ablation: removing bidirectionality costs ~5 pp F1.

### Q8. Why GRU and not LSTM, or Mamba, or Transformer?

- **vs LSTM**: similar accuracy, fewer parameters. GRU was chosen for parameter efficiency.
- **vs Mamba**: explored in earlier iterations (`AION.md` baseline failure analysis). Mamba required CUDA; CPU fallback (Linear Attention) collapsed accuracy to F1=0.145. GRU is CPU-native.
- **vs Transformer**: 2,560 timesteps × 8 heads × N layers = expensive on CPU. GRU is O(n).

### Q9. What's the inductive bias of channel attention?

SE-style attention learns per-channel scaling. After multi-scale CNN, each channel is a fault-frequency feature. Attention says: "for THIS sample, the long-term channel matters more (suggests cage fault) than short-term". Without it, every fault sample is processed with the same channel weighting — empirically loses 5 pp F1.

### Q10. Why not include a transformer head on top?

Tried in the `Enhanced` baseline (4.6M params, F1=0.145). The added complexity caused overfitting on 8K samples. NEXUS's right-sizing (1.06M params for 8K samples) was a deliberate retreat from larger architectures.

## Deployment

### Q11. What hardware do I need?

Inference on CPU:
- 1.5 ms per sample on T4 GPU
- 12 ms per sample on Intel Xeon (1 thread)
- 45 ms per sample on Raspberry Pi 4

For training/fine-tuning:
- Few-shot (head-only): CPU, 5 minutes
- Full retraining: GPU recommended; ~30 min on T4 or 3 hours on CPU

### Q12. Does it run offline / air-gapped?

Yes. The Docker container has no required outbound network connections. Bring your own checkpoint, mount as a volume.

### Q13. How do I integrate with my SCADA / DCS?

OPC UA + MQTT connectors are on the v2.0 roadmap (see `AION_NEXUS_RD/04_PRODUCT_ROADMAP.md`, weeks 4–5). v1.0 ships REST API only. For immediate integration: write a thin OPC UA wrapper around `/predict_long_signal`.

### Q14. Can I run multiple instances in parallel?

Yes. The Docker container is stateless. Scale horizontally with Kubernetes / Docker Swarm. Each instance loads its own checkpoint — use a persistent volume for shared models.

### Q15. What about model updates?

Each release is versioned (semver). The API response includes `model_version`. Plan a canary deploy: 5% traffic on new version for 24 hours, monitor confidence-band distribution + latency, then 100%.

### Q16. How do I monitor the model in production?

- `/health` returns inference count, running latency.
- Log all predictions with timestamp + signal hash + confidence + model version.
- Alert on `confidence_band == "low"` rate above threshold (typical: > 5% of samples → review).
- Alert on cross-class distribution drift (typical: > 20% deviation from baseline → drift).

## Few-shot adaptation

### Q17. What's the minimum sample count for adaptation?

Validated minimum: **4 samples** (1 per class minimum). Recommended: **10 per class** (40 total) for variance-stable lift. See sample-sensitivity curve in `PERFORMANCE_BENCHMARKS.md`.

### Q18. Can I run few-shot multiple times?

Yes — re-running few-shot with new data progressively improves the head. Save adapted checkpoints with version numbers (e.g., `aion_nexus_v1_machine42_2025-11.pth`).

### Q19. Does few-shot adapt the encoder?

No — only the classifier head is fine-tuned. Encoder is deep-frozen via `requires_grad=False`. This prevents catastrophic forgetting and keeps generalization properties intact.

### Q20. Can I unfreeze the encoder if I have lots of target data?

Possible but explicitly NOT supported in v1.0. With > 1000 target samples, full retraining is more reliable than encoder fine-tuning. We can add unfrozen-encoder mode in v2.0 if customer demand exists.

## Edge cases & robustness

### Q21. What happens with NaN / Inf in the input?

Caught by `validate_signal` BEFORE any cropping. Raises `SignalValidationError`. The model never sees NaN-contaminated input.

### Q22. What if my sensor is stuck (constant value)?

Caught by per-channel std threshold. Stuck channel → `SignalValidationError("Channel X appears stuck")`. Refusing to predict prevents confidently-wrong outputs.

### Q23. What sampling rate does the model assume?

25.6 kHz. The receptive field of the multi-scale CNN is calibrated to this rate. For 50 kHz, downsample by 2 first. For 12.8 kHz, upsample (model degrades; consider retraining).

### Q24. What if the signal length is not exactly 2560?

- `< 2560`: `SignalValidationError`. Acquire longer signal.
- `> 2560`: center-crop. The middle 2560 samples are kept. NaN/Inf are checked BEFORE crop, so anomalies in the discarded portion are still detected.

### Q25. What if I have only 1 channel?

The model expects 2 channels. Common workaround: duplicate the single channel to make `[1, N] → [2, N]`. Will work, but expect F1 degradation by ~5 pp (loses cross-channel correlation features).

### Q26. What about line-frequency interference (50/60 Hz)?

Currently no built-in notch filter. **Roadmap P0.3 (week 3)**. For now, pre-filter your signal at the source (most industrial vibration analyzers do this).

### Q27. Variable speed motors (VFD-driven)?

Order tracking preprocessor on roadmap (P1.4, weeks 16–17). For now, the model handles ~±10% speed variation gracefully (its multi-scale design absorbs some shift). Larger variations need retraining or order tracking.

## Concurrency & threading

### Q28. Is `InferenceEngine` thread-safe?

Read-only inference (`.predict()`, `.predict_batch()`, `.extract_features()`) is thread-safe. The model is in eval mode with no dropout. Internal state (running latency average) uses simple integer counters that may race in extreme high-concurrency, but the impact is purely cosmetic (telemetry inaccuracy, not prediction inaccuracy).

`FewShotAdapter.adapt()` is NOT thread-safe — it modifies model parameters. Run adapter calls sequentially or in separate processes.

### Q29. What about GPU concurrency?

Standard PyTorch / CUDA semantics apply. The model is loaded on a single device per `InferenceEngine` instance. For multi-GPU, instantiate multiple engines.

### Q30. What's the dependency graph?

Production runtime:
- `torch ≥ 2.0.0` (PyTorch Foundation, Linux Foundation)
- `numpy ≥ 1.24.0` (NumFOCUS)
- `fastapi ≥ 0.110.0`, `uvicorn`, `pydantic ≥ 2.0.0`, `python-multipart` (for server only)

All actively maintained, MIT-class licenses (Apache 2.0 / BSD / MIT / Python-2.0). No GPL / AGPL.

### Q31. How do you handle CVE patches?

`scripts/audit_supply_chain.py` runs `pip-audit` against the lockfile. Run weekly in CI. Major CVEs trigger a patch release within 7 days.

### Q32. What's your threat model?

See `docs/security.md`. Summary:
- We do NOT trust the input signal (validated by `validate_signal`).
- We DO trust the checkpoint (assume operator placed correct file).
- We DO trust the running environment (container has non-root user; volume is read-only).
- Out of scope: model poisoning attacks (would require attacker with training-time access).

### Q33. Can I deploy in regulated industries (pharma, food)?

v1.0 is NOT certified for FDA 21 CFR Part 11 / ISO 13485 / GxP. v3.0 (months 12+) targets ISO 13374 / 18436-2 + 21 CFR Part 11 documentation crosswalk. For current pharma deployment, treat as advisory tool only with human review of every alarm.

### Q34. How do you compare to SKF Microlog?

SKF: hardware + software combo, $30–100K/site/year, locked to SKF sensors, F1 not publicly benchmarked.
Us: software only, BYOS, $5–50K/site/year, F1 publicly benchmarked at 0.898/0.615/0.672. Different category — we don't sell hardware.

### Q35. How do you compare to Augury?

Augury: $1.5–3K/asset/year fully bundled, sensors + cloud + service. Cloud-only, vendor-locked.
Us: $200–500/asset/year software-only, BYOS. We don't compete on bundling; we win on cost + openness for SME.

### Q36. How do you compare to Senseye (Siemens)?

Senseye: SaaS, $500–1500/asset/year, mostly Siemens-hardware-aligned, 95% accuracy claimed (no public benchmarks).
Us: cheaper, open architecture, public benchmarks. Different value prop.

### Q37. Why not just use OpenAI / Anthropic API?

LLM APIs are not designed for streaming time-series classification. They lack temporal inductive bias, cost ~1000× more per inference, and don't run on edge. Wrong tool for this job.

### Q38. Is there a foundation model I should use instead?

Time-series foundation models (Chronos, Moirai, TimeGPT) are improving. Currently: not zero-shot competitive on bearing fault diagnosis. We'll integrate them as encoder option in v3.0 if they catch up.

## Reproducibility

### Q39. Are training runs deterministic?

PyTorch with `torch.manual_seed(0)` + `torch.use_deterministic_algorithms(True)` gives bit-exact reproducibility on a fixed device. Cross-device (CPU vs GPU vs different GPU model) reproduces F1 within ±0.001.

### Q40. How do I retrain?

The training code is NOT in this production package (separate repo). To retrain:

1. Get the source training repo (separate `motif/` style codebase).
2. Place FEMTO data at expected path.
3. `python train_nexus.py --config nexus_default.yaml`.
4. Best checkpoint saved to `results/nexus_results/best_model.pth`.
5. Copy to `AION_NEXUS_PRODUCTION/checkpoints/aion_nexus_v1.pth`.
6. Run `scripts/verify_checkpoint.py` to confirm F1.

### Q41. Can I train on my own data?

Yes, but you'll need:

- `[2, ≥2560]` vibration signals at 25.6 kHz (or resample to it).
- Labels: 0=normal, 1=early, 2=medium, 3=advanced (or your own taxonomy).
- Temporal ordering preserved (run-to-failure data ideal).
- 5K+ samples for stable training.

Consider few-shot adaptation instead if you have less.

## Internal R&D questions (often asked)

### Q49. What's the relationship between AION-NEXUS and motif/?

`motif/` is sister R&D (separate codebase) exploring multi-scale Koopman RG operators on signals. Its `paradigm probe` discovered a substrate-readout dichotomy (ESN-dense + quadratic readout solves XOR; sparse RHC variants don't). We have a pre-registered experiment (`AION_NEXUS_RD/05_SUBSTRATE_EXPERIMENT_PREREG.md`) testing whether this dichotomy lifts AION cross-domain F1. Outcome PASS/FAIL determines integration. v1.0 is independent of motif.

### Q50. How does the §6.31 retraction discipline relate?

The motif project has accumulated 7 documented retractions (21 across VELLERA + motif total). The methodology — pre-registered binary criteria, locked git SHA, retraction documents on falsification — is applied to AION-NEXUS as well. Any future feature with non-trivial scientific claim must come with a prereg and binary kill criteria.

### Q51. What is "the wedge"?

See `AION_NEXUS_RD/03_DIFFERENTIATION_STRATEGY.md`. Short version: open architecture + reproducibility + 10-sample few-shot adaptation, packaged for SME manufacturing at $200–500/asset/year. None of the 16 competitors analyzed match this position simultaneously.
